# 项目计划：战略与战术

> 活文档。每个阶段结束更新一次；设计变更先改这里，再改代码。
> T0 = 2026-10-26（周一），阶段时间以 T0 起算。

## 0. 一页纸

| 项 | 内容 |
|---|---|
| **战略一句话** | 用可执行的业务语义层（本体），把 Agent 的开放式生成收敛成「封闭域选择 + 可验证计算 + 受控执行」，把特定业务场景的幻觉压到可接受范围 |
| **当前阶段** | P0 垂直切片（设备维保），W4：MCP 与 DeepSeek 接入完成，待真实 key 验证 |
| **下一个里程碑** | 用真实 DeepSeek key 跑一轮评测，补齐依赖 Agent 的对抗用例 |
| **最大风险** | 元模型过度设计，做了平台却没有跑通的场景 |
| **成败标准** | 单域 6 条验收全绿，且新增对象只改 YAML 不改 Java |

## 1. 战略

### 1.1 问题

大模型进企业，卡在三处，RAG 只解决第一个：

1. **上下文不对**：模型不知道「这个客户」在系统里是谁、和哪些订单设备有关；
2. **口径不一致**：同一个「逾期」在三个部门三种算法；
3. **只能聊不能干**：查完要改状态、发工单、冻结额度，缺受控的动作出口。

### 1.2 判断

不要把模型变聪明，**把环境变确定**。

本体 = `semantic`（对象、属性、关系）+ `kinetic`（函数、动作、权限）。它给 Agent 的不是一段 prompt，而是一组带 schema、带前置条件、带权限的工具，以及一套可解释的数据接口。

三个推论：

- 只做对象和关系，是 ER 图，不是本体；
- 只有函数没有动作，永远闭环不了；
- 没有权限与审计，上不了生产。

### 1.3 战略假设（不成立就该停）

| # | 假设 | 怎么验证 | 证伪信号 |
|---|---|---|---|
| H1 | 企业 AI 的主要瓶颈是业务上下文与执行边界，不是模型能力 | 同一模型接入本体前后，评测集可归因错误率下降 ≥ 50% | 下降 < 20% |
| H2 | 业务对象、规则、动作可以被显式建模，成本可接受 | 新域从 0 到可查询 ≤ 2 人周 | > 6 人周且不可复用 |
| H3 | 业务方愿意承担建模 owner | 至少 2 个域有明确 owner 并完成一次发布 | 无人认领，模型变成 IT 自嗨 |
| H4 | 评测集能稳定度量幻觉 | 同一评测集重复跑，结果波动 < 5% | 波动大，说明评测本身不可靠 |

H1 和 H4 是项目的生死线。如果评测本身不稳，后面所有「幻觉下降」都无法证明。

### 1.4 目标（12 个月）

- 3 个业务域上线，每个域有 owner
- 新增对象类型只改 YAML，不改 Java
- Agent 的写操作 100% 走 `propose → execute`，全部有审计
- 单域评测 ≥ 200 条，回归通过率 100%

### 1.5 非目标（明确不做）

- 通用可视化建模 IDE（第一年不做，YAML 足够）
- 多租户 SaaS 化
- 图数据库（递归 CTE 够用）
- AI 自动生成的本体直接上生产（只做草稿辅助，必须人审）
- 预测性维护、生成式分析这类「模型能力问题」

## 2. 战略路径

| 阶段 | 时间 | 主题 | 毕业条件 |
|---|---|---|---|
| **P0 垂直切片** | 0–3 月 | 一个域跑通完整闭环 | 《设备维保》6 条验收全绿 |
| **P1 平台化** | 3–6 月 | 抽公共运行时，接第二个域 | 新域接入只写 YAML + Connector，Java 零改动 |
| **P2 多域治理** | 6–12 月 | 权限体系、影响分析、领域模板库 | 3 域在线，改一个属性能列出影响面 |

三条路径原则，违反任何一条都会返工：

1. **先有场景，再抽象**。没有第二个场景做参照，抽出来的都是错的。
2. **抽象不超过两个场景**。第一次只做「可配置」，不做「可扩展框架」。
3. **每个阶段结束必须有可运行的 demo**。不能演示的阶段等于没完成。

## 3. 战术

### 3.1 架构（已定，P1 前不再改）

```
接入层   Agent 网关（工具生成 / MCP）· REST · YAML 建模
运行时   对象服务 · 函数引擎 · 动作网关 · 动态权限
元模型   16 张表 / 三个 schema（ont_meta / ont_rt / ont_eval）
绑定层   Connector SPI：JDBC 起步
```

代码三个模块：`ontology-core`（元模型）、`ontology-runtime`（运行时）、`ontology-app`（入口）。

### 3.2 技术栈（锁定到 P1 结束）

| 项 | 选择 | 备注 |
|---|---|---|
| 语言 / 框架 | Java 21 + Spring Boot 4.1.1 | 虚拟线程已开 |
| 数据库 | PostgreSQL 17.10 | JSONB + 递归 CTE |
| 迁移 | Flyway 12.4（`spring-boot-starter-flyway`） | Boot 4 必须用 starter，见 README 踩坑 |
| API 文档 | springdoc 3.1.1 | 支持 Boot 4 |
| 构建 | Maven 3.9.16 | 依赖仓库在工程内 `.m2` |
| 容器 | 无（本机无 Docker） | 测试用本地 PG + 临时 schema |

刻意不用：JPA、Spring Security、Lombok、MapStruct、WebFlux、Redis、Neo4j。理由见 [01-meta-model.md](01-meta-model.md) 与对话记录，核心是「别让框架替我们做本体的决策」。

### 3.3 四条工程纪律

1. **本体即代码**：YAML 进 Git，`ont_meta` 可整库重建；库里的定义必须能从 Git 复现。
2. **没有 owner 的属性不允许发布**：证明负担前置，挡掉 80% 的垃圾建模。
3. **函数只读，写只走 Action**：运行时强制，不是约定。
4. **先写评测，再改本体**：每次本体变更都要跑回归，否则不算改完。

### 3.5 生产准入（每个域上线前逐条过）

1. 可解释：任取一个指标，能说出算法、版本、来源表
2. 可拒绝：超出本体词汇时澄清或拒答，有评测用例证明
3. 动作安全：幂等、前置条件、dry-run、补偿（或声明不可回滚）
4. 变更安全：改属性能列出受影响对象，且能在 staging 验证
5. 权限正确：越权测试通过率 100%
6. 数据新鲜：有 SLA，界面能看到「数据是几分钟前的」
7. 可评测：≥ 200 条金标准 + 对抗用例，回归全绿

## 4. 决策记录（ADR 索引）

| # | 决策 | 理由 | 代价 | 复审时机 |
|---|---|---|---|---|
| D1 | 逻辑对象与版本分离 | 动作/权限引用逻辑 id，升版不悬空 | 多一张表，loader 复杂一点 | P1 结束 |
| D2 | 虚拟化优先，不搬数据 | 避免同步地狱 | 复杂遍历性能受限 | 出现跨源遍历瓶颈时 |
| D3 | 函数只读，写走 Action | 幻觉治理核心：数值来自函数不来自模型 | 动作开发成本高 | 不复审 |
| D4 | 权限是数据（`PROPOSE`/`EXECUTE` 分离） | Agent 只能提议不能直接执行 | 运行时要做策略求值 | 不复审 |
| D5 | 不用 JPA / 不用 Spring Security | 动态 SQL 与数据驱动权限，框架会反客为主 | 手写 SQL 与过滤器 | P2 引入 OIDC 时只补认证 |
| D6 | 三 schema 分离 | 生命周期、权限、备份策略不同 | 跨 schema 写 SQL 略繁琐 | 觉得麻烦就合并 |
| D7 | 评测进元模型（`eval_case`） | 让「幻觉有没有变差」可 CI 断言 | 需要业务专家标注 | 不复审 |

完整论证见 [01-meta-model.md](01-meta-model.md)，表关系见 [03-schema-explained.md](03-schema-explained.md)。

## 5. 风险登记册

| 风险 | 概率 | 影响 | 触发信号 | 应对 |
|---|---|---|---|---|
| 元模型过度设计 | 高 | 高 | 三个月还在改元模型，没有 demo | 只做可配置，不做框架；每周必须能演示 |
| 没有 killer 场景 | 中 | 高 | 找不到愿意出 owner 的域 | 先用设备维保自证，再找业务 |
| 数据同步地狱 | 中 | 高 | 开始为建模搬数据 | 坚持 VIRTUAL 优先，物化需评审 |
| 权限后补导致返工 | 中 | 高 | 业务写操作先上线再补权限 | W3 前不做任何写操作 |
| 评测缺失，无法证明效果 | 高 | 高 | 「感觉变好了」成为唯一证据 | W1 立 10 条，W4 覆盖全部动作，W12 扩到 200 |
| Boot 4 生态踩坑 | 中 | 中 | 依赖不触发、自动配置拆分 | 已踩 2 个，全部记入 README |
| 单人推进，时间不足 | 高 | 中 | 连续两周无交付 | 每阶段 4 周，宁可砍范围不砍闭环 |
| 业务方把本体当知识库 | 中 | 中 | 需求全是「问答」「检索」 | 用「有没有 Action」作为立项门槛 |

## 6. 已知债务

| 债务 | 影响 | 处理阶段 |
|---|---|---|
| 关系未版本化 | schema 改动可能让 join 失效 | P1（发布时校验列存在） |
| 表达式沙箱未实现 | `precondition_expr` / `row_filter_expr` 无法安全求值 | W3 |
| 实体解析（多源同一对象） | 同一设备在不同系统 id 不同 | P2 |
| 跨域引用机制 | 域之间只能引用公共对象，准入未定 | P2 |
| 无建模 IDE | 业务方无法自助建模 | P1 之后再评估 |

## 7. 治理方式

- **文档优先**：设计变更先改文档与 ADR，再改代码；代码与文档不一致时以文档为准，直到文档被更新。
- **每周一次 demo**：能跑的东西才算进度，PPT 不算。
- **每阶段末**：更新本文件 + 新增一条 ADR + 一页复盘（做对了什么、下次不做什么）。
- **评测即门禁**：本体发布前跑 `eval_case`，不绿不许发。

## 8. 现在做什么（W4 收尾）

已完成：

- **MCP 工具层**：24 个工具（7 对象 × 2 + 5 函数 + 5 动作），JSON-RPC 端点 `/mcp`，工具名/描述/入参 schema 全部由元模型生成。
- **脚本化 Agent**：`scripts/mcp-agent-demo.ps1` 走完「站点 → 设备 → 函数 → 提议 → 被拒」，验证工具契约与权限边界。
- **DeepSeek 接入**：`POST /api/agent/ask` 做 function-calling 循环（模型选工具、我们执行、结果回填），`/api/agent/preview` 可先看 payload；已用本地桩服务验证完整循环。
- 新增对象/函数/动作不需要改 Java，重新发布本体即可。

剩余：

1. **真实模型验证**（待 key）：配置 `DEEPSEEK_API_KEY` 后跑一轮，确认工具选择与拒答行为符合预期。
2. **对抗用例**：`mustRefuse` / `mustAskClarify` 依赖模型行为，接上模型后才有判定意义。
3. **关系遍历下推行过滤**（W3 遗留）：从站点查设备时，设备自身的行过滤尚未参与。

接模型后的验收：同一问题能在 `audit_log` 里还原工具调用序列；越权与拒答用例通过。

## 9. W3 复盘

- **做对了**：先做权限再做动作，越权路径在写库之前就被挡住；幂等键用表达式派生，重复请求天然去重。
- **下次改进**：约束与代码的枚举值要对齐（`audit_log.operation` 漏了 APPROVE/REJECT，直到审批时才炸）；前置条件里的变量命名要有统一约定（对象类型 code，不是别名）。
- **遗留**：关系遍历没有下推行过滤（从站点查设备时设备自身的行过滤不生效），需要 W4 补。
